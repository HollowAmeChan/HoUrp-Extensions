# URP 自定义材质与 Shader 体系重构文档

> RP 第十阶段先按 `Documentation~/rp重构第十步执行计划.md` 推进。该阶段不直接迁移完整材质包，而是先冻结新材质系统接入 `HoUrp-Extensions` 的 shader ABI、AOV 输出契约、Feature Block / Preset 模型和最小 generated shader 原型。

## 1. 背景与问题

你当前在自研 URP 管线中魔改 liltoon / lilpbr，并逐步把其作为材质系统的辅助基础。但在实际推进中，已经出现了明显的架构瓶颈：

- **lilpbr 的 UI 包装层过重**，材质面板与 shader 结构绑定过深。
- **反射驱动的变体编译**导致编辑器卡死、编译爆炸、调试成本极高。
- **liltoon 虽然更接近可维护方向**，但它仍然属于兼容性很强、历史包袱较多的体系。
- 你自己的管线里还有一个较重的 **HOAOV pass**，并且未来还要接入更多 RenderFeature。
- 你希望的不是“能跑就行的 shader 包”，而是一个 **可以长期反复调试、升级、扩展、控制变体数量的材质编译系统**。

因此，当前遇到的问题不是单纯的 SSS 实现问题，而是：

> 材质 UI、shader 结构、pass 组织、变体策略、RenderFeature 依赖已经耦合到无法稳定迭代。

---

## 2. 核心判断

你的方向是对的：

### 2.1 不应该继续依赖“厚 UI + 动态 keyword 地狱”

所谓“厚 UI”，指的是：

- UI 负责大量逻辑分发
- UI 通过反射或约定自动触发 shader keyword
- UI 与 shader 编译路径强耦合
- UI 一改，shader 变体、pass、材质布局一起变动

这种结构在简单项目里还能工作，但在你这种“管线级 + 高自定义 + 多 RenderFeature”场景中，会很快变成灾难。

### 2.2 更适合你的，是“静态组合式 Shader Pipeline”

也就是：

- **在编译前确定结构**
- **有限组合，而不是无限开关**
- **UI 只做参数展示与预设切换**
- **shader 结构由生成器或模板系统固化**
- **变体数量受控，模块边界清晰**

这更接近“引擎级材质系统”，而不是传统 Unity Inspector 的写法。

---

## 3. 设计目标

你的新体系应该明确服务于以下目标：

### 3.1 Shader 结构稳定

一个 shader 的 pass、输入输出、include 依赖关系尽量固定。

### 3.2 变体可控

所有组合都必须是预定义的，不允许随材质随意动态生成组合爆炸。

### 3.3 Pass 可复用

Forward、ShadowCaster、DepthOnly、HOAOV 等 pass 尽量标准化。

### 3.4 RenderFeature 可对接

你的 HOAOV、SSS、阴影、SSAO 等模块需要有统一数据入口，不应彼此混写。

### 3.5 UI 轻量化

UI 只做最基本的：

- 折叠
- 分组
- preset 切换
- 少量参数编辑
- 小型预览/贴图槽

UI 不参与 shader 结构编排。

---

## 4. 结论：你应该离开 lilpbr 的 UI 体系

### 4.1 为什么要离开

lilpbr 的问题不只是“写法老”，而是它的整体组织方式与当前需求不匹配：

- 它倾向于用 UI 包装 shader 功能
- 它倾向于让材质面板控制大量内部结构
- 它依赖反射、keyword、编译宏等方式进行状态切换
- 它不适合承载一个大而复杂的自定义 RP 管线

这类结构一旦加入复杂 SSS、HOAOV、大量 feature，就会迅速失控。

### 4.2 liltoon 可以借鉴，但不应直接继承

liltoon 比 lilpbr 更适合参考的点在于：

- shader 是组装式的
- pass 通过 block / include 组合
- 结构更接近“编译器拼装”而非“大一统材质面板”

但 liltoon 仍然有：

- 大量兼容性宏
- 较多 keyword
- 历史遗留结构
- inspector 与 shader 之间仍有较强耦合

所以最佳策略不是“继续改 liltoon”，而是：

> 参考它的 block 化思想，自己建立一套更克制、更工程化的材质编译系统。

---

## 5. 总体架构建议

你应该把系统拆成四层：

1. **Shader Template 层**
2. **Feature Block 层**
3. **Material Preset 层**
4. **Generated Shader 层**

---

## 6. 第一层：Shader Template

这一层只定义“骨架”，不负责具体 feature 的复杂逻辑。

### 6.1 作用

- 固定 pass 顺序
- 固定 pragma 结构
- 固定输入输出 ABI
- 固定各类 include 入口

### 6.2 示例

可以按用途拆模板：

- `CharacterForward.template`
- `CharacterShadow.template`
- `HOAOV.template`
- `TransparentForward.template`
- `DepthOnly.template`

### 6.3 原则

模板层只做：

- 结构框架
- 编译入口
- 引用 feature block

不要在模板里写大量业务逻辑。

---

## 7. 第二层：Feature Block

这是你最重要的一层。

### 7.1 作用

把 shader 功能拆成独立模块，例如：

- Lighting
- SSS
- Shadow
- AO
- Specular
- Rim
- Hair
- ClearCoat
- HOAOV 输出

### 7.2 示例目录

```text
Features/
    Lighting/
        ToonLighting.hlsl
        PBRLighting.hlsl

    SSS/
        SSS_None.hlsl
        SSS_Skin.hlsl
        SSS_Wax.hlsl

    Shadow/
        Shadow_None.hlsl
        Shadow_Soft.hlsl
        Shadow_PCSS.hlsl

    HOAOV/
        HOAOV_Character.hlsl
        HOAOV_Transparent.hlsl
```

### 7.3 约束

每个 feature block 应该遵守：

- 输入输出清晰
- 不直接依赖 UI
- 不自己决定全局结构
- 尽量只依赖统一的 SurfaceData / Varyings ABI
- 可独立测试

---

## 8. 第三层：Material Preset

这一层负责定义“这类材质到底由哪些 feature 组成”。

### 8.1 作用

- 决定使用哪个模板
- 决定启用哪些 feature block
- 决定固定的 pass 组合
- 决定材质参数的默认值与展示方式

### 8.2 预设例子

- `Character_Toon`
- `Character_Toon_SSS`
- `Character_PBR`
- `Character_PBR_SSS`
- `Hair_Toon`
- `Environment_PBR`
- `Transparent_FX`

### 8.3 预设的价值

你不应该允许材质在运行时随便拼装出一个全新的结构，而是让用户从预设中选：

- 这是 toon 角色
- 这是带皮肤 SSS 的角色
- 这是透明特效
- 这是环境材质

这样你的变体空间是可控的。

---

## 9. 第四层：Generated Shader

这是最终生成并进 Unity 的 `.shader` 文件。

### 9.1 作用

- 作为最终编译产物
- 面向 Unity 与渲染管线
- 由模板 + feature + preset 生成

### 9.2 优势

- 便于版本控制
- 便于 diff 和调试
- 便于定位问题
- 便于做批量升级
- 避免在编辑器里实时拼装导致的灾难

---

## 10. UI 设计原则

这是你当前最应该重构的地方之一。

### 10.1 UI 的职责

UI 只负责：

- 折叠分组
- 少量参数编辑
- 贴图槽
- preset 选择
- 基础预览

### 10.2 UI 不应该做的事

UI 不应该：

- 自动决定 shader 结构
- 反射扫描后生成复杂 keyword 关系
- 动态决定 pass 有无
- 在编辑器中触发过多编译分支
- 与底层 feature 强耦合

### 10.3 UI 应该做轻

你提到“折叠就够了，图片槽做小一点”这个判断非常合理。对于这种系统，UI 需要的是：

- 清晰
- 稳定
- 快速
- 不干扰结构

而不是“看起来很聪明”。

---

## 11. 变体策略：只允许固定组合

这是整个体系能否长期稳定的关键。

### 11.1 为什么不能开放式动态组装

开放式组合的问题是：

- 变体数量指数爆炸
- 编译时间不可控
- 调试复杂度上升
- 不同模块之间的兼容性变差
- 资源审核和迭代成本极高

### 11.2 你应该采用的策略

只允许预先定义好的组合，例如：

- Shadow 有 / 无
- SSS 有 / 无
- SSAO 有 / 无
- HOAOV 有 / 无
- Hair 模式 / Character 模式

这些组合必须在工程层被列举出来，而不是运行时随意拼。

### 11.3 结果

这样做的结果是：

- shader 数量会增加
- 但每个 shader 更简单、更稳定
- 变体边界更清楚
- 出问题时更容易定位

在你的场景里，**shader 多不是问题，失控才是问题**。

---

## 12. SurfaceData ABI：模块之间通信的核心

如果你未来要让各 feature block 协同工作，最重要的是定义一个稳定的数据接口。

### 12.1 为什么要 ABI

因为你不能让各个 feature block 互相乱 include、乱读变量、乱写状态。

你需要一个统一的“材质数据契约”。

### 12.2 示例

```hlsl
struct SurfaceData
{
    half3 baseColor;
    half3 normalWS;
    half metallic;
    half roughness;
    half sssMask;
    half ao;
    half emissive;
};
```

### 12.3 好处

- 所有模块统一输入输出
- AOV/HOAOV 可以直接读取统一结构
- 以后新增 feature 时不容易破坏旧系统
- 调试更容易做数据对照

---

## 13. HOAOV 在体系里的位置

你提到自己有一个很重的 HOAOV pass，这意味着你的系统不能只围绕普通 forward lighting 来设计。

### 13.1 HOAOV 应该作为一级公民

也就是说：

- 它不是附属 debug
- 不是临时补丁
- 而是管线结构的一部分

### 13.2 统一输出结构

所有角色 shader 最好都能输出一套稳定的 HOAOV 数据，例如：

- baseColor
- normal
- roughness
- sssMask
- emission
- materialId

### 13.3 设计收益

这样你的 RenderFeature 可以：

- 对所有材质使用统一读取逻辑
- 避免材质之间的分裂实现
- 更容易做离线/实时分析
- 更容易做调试与回放

---

## 15. 推荐的开发流程

### 15.1 先定 ABI

先把：

- SurfaceData
- Varyings
- Pass 输入输出
- HOAOV 输出格式

全部定下来。

### 15.2 再定模板

先把基础 pass 骨架固定。

### 15.3 再拆 feature

把 SSS、Shadow、Lighting、AO、HOAOV 分别拆成独立 block。

### 15.4 最后做生成器

让生成器负责拼模板和 feature，产出最终 shader。

### 15.5 UI 最后补

等系统稳定后，再做轻 UI。

---

## 16. 调试与迭代策略

因为你的项目后面一定会经历大量迭代，所以要一开始就考虑调试方式。

### 16.1 保持生成结果可读

生成后的 `.shader` 文件应该尽量能直接看懂。

### 16.2 保留 source mapping

最好能知道某段生成代码来自哪个模板或 feature block。

### 16.3 预设校验

每次生成前做静态校验：

- 是否缺少必需 feature
- 是否引用了不存在的 block
- 是否某些组合非法
- 是否某 pass 的 ABI 不一致

### 16.4 控制变体爆炸

在生成器层面就限制非法组合，而不是等到 Unity 编译时再崩。

---

## 17. 你当前最应该避免的坑

### 17.1 不要继续在 lilpbr 上无限堆功能

它已经超出原始设计边界。

### 17.2 不要让 UI 反向决定 shader 结构

这是变体灾难的起点。

### 17.3 不要追求“单 shader 包所有情况”

那会导致编译和维护都极其困难。

### 17.4 不要让 feature block 彼此乱耦合

模块之间应通过 ABI，而不是互相 include 细节。

### 17.5 不要让运行时系统决定编译期结构

结构变化必须在生成阶段完成。

---

## 18. 建议的落地顺序

一个比较稳的实施顺序是：

1. 先定义 `SurfaceData` 与 `Varyings`
2. 先固化 Forward / Shadow / HOAOV 的 pass 框架
3. 把 SSS 做成独立 feature block
4. 把 Lighting 与 Shadow 拆成多个固定模块
5. 建立 preset 描述文件
6. 建一个最小 shader 生成器
7. 把 UI 改成轻量 preset 面板
8. 最后再做高级调试工具

---

## 19. 最终结论

你当前的判断可以总结成一句话：

> 你需要的不是一个更复杂的 shader UI，而是一套可控的材质编译系统。

更具体一点：

- **离开厚 UI 体系**是对的
- **参考 liltoon 的 block 化思路**是对的
- **固定 pass / 固定组合 / 固定 ABI**是对的
- **UI 轻量化**是对的
- **让生成器负责结构，让 UI 负责展示**是对的
- **让 HOAOV 成为一级结构**也是对的

你的方向已经从“改 shader”转向“设计 RP 级材质架构”了。这个阶段最重要的不是功能堆得多，而是结构是否稳定、是否可迭代、是否能控制复杂度。

如果你把这套体系搭起来，后面无论是 SSS、阴影、SSR、AO、毛发、透明、后期 AOV，都能比较自然地挂进去，而不是再一次被 inspector 和 keyword 的泥潭拖住。
